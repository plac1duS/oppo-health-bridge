# 欢太健康桥：电脑本地版设计

日期：2026-10-24（Asia/Shanghai）

状态：范围按用户最新指示收敛；已完成真机读取可行性验证（见第 10 节），同步/存储/MCP 程序尚未实现。

## 1. 当前决定

用户使用 OPPO Watch 4 Pro、欢太健康及本人已 Root 的手机，不熟悉编程。目标是让 AI 通过 MCP 查询健康数据，同时可以保存、导出自己的记录。

用户最新明确：**数据保存在电脑，手动同步，以后再考虑自动化。** 这替代此前的手机每天 23:30 同步与托管云设计。第一版不开发手机定时服务、云数据库或公网接口，不要求注册云服务或支付托管费用。

主产品为 Windows 中文工具，配套 SQLite 数据库和只读 stdio MCP。手机仅承担数据来源角色；只有实际读取兼容性要求时才增加导出辅助模块，不预先开发独立 Android 产品。

## 2. 使用流程

1. 先让手表正常同步到欢太健康，再用 USB 连接手机和电脑。首次需要在手机确认调试授权，读取私有数据时按实际方案授予所需 Root 权限。
2. 电脑工具检测手机型号、Android、欢太健康版本和必要组件，不要求用户手动查一长串技术参数。发现 Root 不代表加密数据库就可读。
3. 首次提供“同步全部可读取历史”和“仅同步最近数据”，显示各指标进度、条数和实际起止日期，可以中断续传。
4. 后续点击“立即同步”，读取新增数据及修订，保存到同一本地数据库。不是只读当天数据，而是从上次成功位置补齐。
5. 手机断开后，支持本机 MCP 的 AI 客户端仍能查询已保存的数据。结果显示最后成功同步时间和实际覆盖范围。
6. 可按日期导出 CSV / JSON，备份和恢复数据库。

电脑关闭时不提供查询服务。没有点击同步时不会主动更新。“全部历史”仅指实际能读取的本人记录，不包含无法访问或已清理的数据。

## 3. 数据源选择

数据流：手表 → 欢太健康 → 手动采集 → 电脑 SQLite → 本地 MCP → AI。

| 路线 | 用途 | 必须实测的条件 |
| --- | --- | --- |
| USB + Root 读取手机本地数据 | 默认先验证的路径 | 手机连接、数据库加密、App 版本、读取时一致性；必要时才引入适配模块 |
| 读取本人欢太账号已有的云端记录 | 本地读取难以实现或历史缺失时的备选 | 本人凭证、接口可用性、字段含义、网络兼容性和历史范围 |

USB 是连接方式，不代表已经确定解密或导出方法。先探测再选一条可行路径，不为第一版同时实现两套采集器。

第二条路线只从欢太原有服务下载数据，结果仍存在电脑，不使用 Supabase 等新的托管存储。采用它时明确告知需要联网和本人账号授权，不能静默切换。上游接口可调用不代表本用户设备已支持。

两个上游项目均已有静态审查。可参考数据访问逻辑，但不沿用已发现会漏记录、覆盖缓存或把失败当成功的实现。复用代码保留来源、版权及许可。

## 4. 简化组件与存储

- 中文本地界面：连接检测、首次范围选择、立即同步、暂停/继续、状态和导出。
- 数据源适配器：读取本人记录，返回原始内容、来源、记录身份及版本。
- 同步与存储：分页、事务入库、去重、更新合并和持久检查点。
- 标准化查询：按时间和指标查询，保留单位、时区、来源及缺失说明。
- 本地 MCP：由兼容客户端启动查询进程，不部署公网服务。

优先采用 Python 与 SQLite，界面实现按本机依赖选择，不引入容器或独立服务集群。若采用浏览器本地界面，只绑定回环地址，并校验本地会话和请求来源，不开放局域网。

数据库默认位于 `%LOCALAPPDATA%\OPPOHealthBridge\health.db`，界面提供“打开数据文件夹”。真实数据、数据库密钥和账号凭证不进入 Git。凭证分开存储并使用 Windows 保护机制；没有实现验证的数据库加密不作承诺。

## 5. 第一版内容

优先实测心率、睡眠及分期、步数、血氧。压力、HRV、腕温和运动记录根据用户实际数据逐项加入，未经验证不显示为已支持。

导出 CSV / JSON：嵌套结构保留在 JSON，CSV 按指标拆分并正确处理逗号、引号、换行、空值和单位。读取和导出不修改欢太健康源数据。

自动同步、手机后台 App、云托管、随时远程访问、任意品牌导入、完整心电波形和运动轨迹不在第一版承诺中。不为后续扩展提前增加部署复杂度。

## 6. MCP 查询草案

以下工具尚未实现：

| 工具 | 用途 |
| --- | --- |
| `health_status` | 本地数据库状态、最后成功同步、可用指标、最近错误 |
| `health_coverage` | 各指标已检查与实际有数据的日期范围 |
| `health_daily_summary` | 指定范围每日汇总 |
| `health_sleep` | 睡眠区间、分期和来源 |
| `health_timeseries` | 指标时间序列，带分页和截断说明 |

同步、导出和恢复由用户在本地工具中发起；MCP 默认只读，不开放任意 SQL。返回来源、发生时间、单位、时区、同步时间和缺失情况。缺数据不是零，摘要不冒充完整明细。

本地保存不等于模型在本地。使用云端 AI 时，查询结果会发送给对应服务；默认只返回所需的指标和时间范围，凭证永远不作为结果。

## 7. 正确性与恢复

- 按来源、账号、设备和源记录身份去重，修订更新同一记录；不能仅用日期作主键或整行哈希识别修订。
- 分页遵循实际游标规则，不能仅凭最大时间戳跳过同时间戳其他记录。
- 每页数据和检查点事务提交。中断保留已成功部分，失败不报成功，不删除未确认保存的唯一副本。
- 全量与增量沿用同一记录身份，重复同步不重复计数。
- 优先按来源修改版本补新记录和修订。没有版本时回查最近 7 天并提供全量重核；说明这无法保证发现更久以前的修订。
- 区分未同步、无记录、不支持、凭证失效、部分完成和失败。
- 保留原始时间戳及偏移，查询默认 Asia/Shanghai；跨午夜睡眠、午睡和晚到分期按完整记录处理。
- 日统计和明细不能重复累计；腕温偏移、HRV、压力等不明确字段不自行推断单位。
- 读取运行中的手机数据库使用一致快照或合适的读取方式，不能只复制主文件而漏掉 WAL 中的数据。
- 日志不输出凭证或原始健康数据，版本不兼容明确报错，已有数据仍可查询。
- SQLite 备份与恢复必须保持一致，模式迁移前备份；CSV 导出不替代可恢复的数据库备份。

## 9. 下一步

读取可行性已验证（第 10 节），接下来：

1. 字段语义：逐表确认时间戳格式与时区、单位、来源/设备标识、记录身份主键、修订判据，先覆盖心率、睡眠及分期、步数/运动、血氧。只读取字段结构与少量样本核对，不把个人数值写入仓库。
2. 决定导出架构（两条都已被证明或接近可行，择一先做）：
   - **离线解密**：抓取一次口令 + 一致性快照（主库 + WAL），在电脑上用标准 SQLCipher-4 解密为明文 SQLite 后入库。最贴合“电脑本地、断开手机仍可用”，但当前在 App 进程内用非 Room 方式二次打开既有库会报 `SQLITE_CANTOPEN(14)`（口令已确认正确，疑为 App 定制 `libsqlcipher.so` 默认参数差异），需先解决或改用下一条。
   - **活句柄导出**：USB 连接时用 App 自身已打开的 SQLCipher 句柄 `sqlcipher_export` 出明文快照再入库。最稳（复用 App 精确配置），但每次同步需要 App 运行 + Frida。
3. 按选定架构实现采集→去重/增量→本地 SQLite 入库→标准化查询→只读 MCP，再按第 8 节验收。

## 10. 真机验证结果（2026-10-24）

仅在本人设备、只读操作，未修改欢太健康源数据，未提交任何个人数据或口令进仓库。

- 设备与应用：小米 14（Android 16），已 Root（KernelSU）。欢太健康 `com.heytap.health` 6.9.37（versionCode 6093700，targetSdk 36）。与此前静态审查的 APK 版本一致。
- 数据库：`/data/data/com.heytap.health/databases/database.db` 约 400 MB，WAL 模式，文件头随机（非 `SQLite format 3`），为 SQLCipher-4 加密。另有 `cipher_open_usercenter.db`、`creation_encrypted.db` 等小库。
- 加密与口令：主库口令由 `com.heytap.health.base.database.DBKey.initDbKey` 提供，经 `AesGcmAndroidKeyStore`（Android Keystore AES-GCM）解包；`DataProcessDelegateImpl` → `DBKey` 为实际实现。口令为 38 字符文本（PRAGMA KEY 口令，非裸密钥）。`AppDatabase$1.preKey` 为空、`postKey` 仅执行校验查询，无自定义 cipher PRAGMA，即标准 SQLCipher-4 默认参数。
- 读取方式：Frida 挂接运行中的 App，调用其 `DelegateInit` 注册 `BusinessDelegate` 依赖后，经 `AppDatabase`（Room）打开主库并查询。主库平时按需打开，首页用缓存不开库，故需触发或经此法打开。
- 结果：枚举出 103 张表，并成功读取 `DBHeartRate`/`DBSleepTable`/`DBBloodOxygenSaturation`/`DBSportDataDetail`/`DBSportDataStat` 等核心表的真实记录（覆盖多年历史）；`DBMetricData`、`DBHrvTable` 为空（HRV 可能存于他表或未采集）。
- 未决：App 进程外（或非 Room 路径）用口令二次打开既有库报 `SQLITE_CANTOPEN(14)`，离线解密路径需先解决；运动轨迹与心电波形仍待逐项确认。字段语义见[字段映射](../research/2026-10-24-field-mapping.md)。

## 11. 第一版实现进度（2026-10-24）

架构选定 **活句柄读取（B）**：Frida 注入运行中的 App，经 `DelegateInit` 注册依赖后用 App 自身 SQLCipher 句柄只读查询。离线解密（A）因 `CANTOPEN(14)` 未通，留作后续可插拔后端（采集层已抽象为 `Reader` 接口，上层不依赖具体后端）。

已实现并真机验证（`bridge/` 包）：

- `config.py` 指标规格（主键、`modified` 游标列、事件时间列与类型）；`device.py` 设备检测 + frida-server 自动推送/拉起 + 拉起 App；`agent/read_agent.js` 只读代理（`ensure/select/tables`）；`reader.py` 挂接与查询；`store.py` 本地 SQLite（忠实镜像源 DDL、按源主键 `INSERT OR REPLACE`、持久化游标/回填下限）；`sync.py` 按 `(modified, rowid)` keyset 增量/可续传；`cli.py` `detect/sync/status`。
- 增量正确性：首轮取最近 N 天后，再次 `sync` 各指标取 **0 行**（含大表小表均不重复计数，游标生效）。
- 数值正确性：本地库 `DBSleepDayStat`/`DBHeartRateDataStatTable`/`DBSportDataStat` 等与 App 对照一致（睡眠分期、心率日汇总、步数/距离/卡路里、血氧、心率逐点）。

每次同步前置条件：USB 已授权、Root、frida-server（自动推送，版本须 = PC 端 frida）、App 进程存活、手表已先同步到 App。

标准化查询 + 只读 MCP（已实现并测试，`bridge/query.py` + `bridge/mcp_server.py`）：

- `query.py` 五类查询，结果带单位、时区(Asia/Shanghai)、来源表与新鲜度，并区分“未同步/无记录/有数据”（缺数据为 null，非 0）：`health_status`、`coverage`、`daily_summary`、`sleep`、`timeseries`。
- `mcp_server.py` 手写 stdio JSON-RPC（换行分隔，零依赖），暴露 `health_status / health_coverage / health_daily_summary / health_sleep / health_timeseries`；只读、不开放任意 SQL、不连手机、不返回凭证或原始加密数据。`python -m bridge serve-mcp` 启动。
- 已用脚本化握手验证：`initialize` → `tools/list`(5) → `tools/call` 各工具返回正确且与 App 一致（睡眠分期、按日汇总、逐点分页）。

导出与备份（已实现并测试，`bridge/export.py` + `bridge/backup.py`）：

- 导出：CSV 按指标拆分（标准转义、本地时间、单位），JSON 保留嵌套汇总（状态/覆盖/每日/每夜），另出 manifest；逐点序列在 CSV。只读本地库，不改源数据。实测导出 `daily_summary/sleep_nights/heart_rate_points/spo2_points/export.json/manifest.json`，数值与 App 一致。
- 备份/恢复：用 sqlite3 在线备份 API 做一致快照（非文件复制）；恢复前自动备份当前库、校验来源、原子替换，可逆。实测 backup→restore 往返行数不变，未加 `--yes` 拒绝执行。

图形界面（已实现并构建自测，`bridge/gui.py` + 根目录 `启动健康桥.bat`/`run-gui.bat`）：Tkinter 标准库、不开网络；一窗完成连接检测、范围选择、立即同步（后台线程 + 可停止续传）、状态表、导出、备份/恢复、打开数据文件夹。耗时操作走后台线程 + 队列回传，界面不卡。无头构建 + 事件循环自测通过。

至此第一版功能齐备：检测 / 同步 / 存储 / 查询 / MCP / 导出 / 备份恢复 / 界面，均已真机或自测验证，且满足第 8 节验收的核心条目（连接探测、小样本验证、手动同步可续传、MCP 联调、双击交付）。

后续打磨（非第一版承诺）：`sport_mode` 代码表与运动轨迹/心电按需取用；`sleep_score`/`standard_time`/`total_duration` 语义；离线解密后端（解决 `CANTOPEN(14)`）；打包为免 Python 环境的安装包；`sync --full` 完整历史回填的耗时优化。
